# Phase 0 Research: Gym Mode Natural Language Workout Logging

**Feature**: `002-gym-voice-logging`  
**Date**: 2026-11-17  
**Branch**: `feature/002-gym-voice-logging`  
**Status**: Completed

## 1. Technical Objectives & Constraints

The goal of this feature is to deliver an in-gym, low-friction voice logging capability for iPhone users, capturing spoken workout details for compound lifts and weighted calisthenics, parsing them into structured sets and reps, displaying an immediate visual review card, and persisting confirmed records to the PostgreSQL database.

### Core Architectural Decisions & Trade-offs

1. **Client-Side Dictation vs Server-Side Audio Processing**:
   - **Decision**: Client-side text transcription via iOS Safari / Web Speech API (or native iOS dictation keyboard). The mobile client submits text strings to `POST /api/v1/gym/parse`.
   - **Rationale**: Audio encoding, upload bandwidth in gyms (often poor cellular/Wi-Fi coverage in basements), and server-side Whisper CPU/GPU container overhead are eliminated. Latency from speech end to parsed preview is under 500ms.
   - **Constitution Compliance**: Principle I (Self-Hosted Architecture) and Principle III (Multimodal Ergonomics & Robustness) are upheld; no raw audio streaming to unvetted cloud endpoints.

2. **Deterministic Natural Language Parsing Engine**:
   - **Decision**: Hybrid Grammar & Multi-Pass Regex Parser combined with Rapid Fuzzy Token Matching (`rapidfuzz` / Levenshtein distance).
   - **Pattern Categories Handled**:
     - *Standard format*: `"5 sets of 8 reps at 185 pounds on back squat"`, `"3x5 bench at 225 lbs"`
     - *Multi-set shorthand*: `"5 by 8 back squat 185"`, `"3 sets of 10 pullups with 25 pounds added"`
     - *Bodyweight modifiers*: `"extra 30 pounds"`, `"plus 25 lbs"`, `"bodyweight only"`, `"assisted dips minus 20 pounds"`
     - *Plate math / vernacular*: `"two plates"` $\to$ 225 lbs, `"one plate"` $\to$ 135 lbs, `"the bar"` $\to$ 45 lbs (with lbs/kg profile awareness)
     - *RPE & Rest*: `"at RPE 8.5"`, `"felt like RPE 9"`, `"2 reps in reserve"`, `"rest 2 minutes"`
   - **Rationale**: Deterministic parsing executes in <2ms, requires no LLM tokens or API latency, runs completely offline-friendly on self-hosted CPU, and provides 100% reproducible testability.

3. **Strict Pre-defined Exercise Taxonomy with Fuzzy Alias Resolution**:
   - **Decision**: Curate a standard catalog of 120+ core exercises (squats, deadlifts, presses, rows, pull-ups, dips, lunges, Olympic lifts, machine movements) seeded into `strength_exercises`.
   - Each exercise has canonical attributes: `slug`, `canonical_name`, `category` (`barbell`, `dumbbell`, `bodyweight`, `machine`, `cable`), `primary_muscle_group`, `is_bodyweight`, and `default_unit`.
   - Associated `exercise_aliases` table and in-memory trie/fuzzy index resolves synonyms:
     - `"back squat"`, `"squats"`, `"squat"`, `"high bar squat"` $\to$ `barbell-back-squat`
     - `"pullups"`, `"pull-up"`, `"chin up"`, `"weighted pullup"` $\to$ `pull-up`
     - `"bench"`, `"flat bench"`, `"flat bench press"` $\to$ `barbell-bench-press`
   - If match score is below confidence threshold (0.75), return top 3 closest catalog options with `is_ambiguous=True` for 1-tap resolution.

4. **Staging & Confirmation Flow (UI/UX)**:
   - **Decision**:
     1. Athlete speaks $\to$ Client sends text transcript to `POST /api/v1/gym/parse`.
     2. Backend parses into structured JSON candidate:
        ```json
        {
          "transcript": "3 sets of 12 pullups with an extra 30 pounds added",
          "exercise": {
            "id": "uuid...",
            "name": "Pull-Up",
            "is_bodyweight": true
          },
          "sets": 3,
          "reps": 12,
          "weight": 30.0,
          "weight_unit": "lbs",
          "is_bodyweight": true,
          "added_weight": 30.0,
          "rpe": null,
          "confidence": 0.96,
          "is_ambiguous": false
        }
        ```
     3. Mobile UI renders a clean card: **Pull-Up | 3 sets × 12 reps | +30 lbs**.
     4. Athlete taps **Confirm** (or taps any field to tweak).
     5. Client calls `POST /api/v1/gym/sessions/{session_id}/sets` with an `idempotency_key` (UUID generated by client) to atomically write to `strength_sets`.

## 2. Dependencies & Tooling

- `rapidfuzz>=3.6.0`: Fast C++ Levenshtein string matching for alias resolution with zero external services.
- `pydantic>=2.7.0`: Schema validation and structured serialization.
- `SQLAlchemy 2.0 (async)` & `Alembic`: Schema evolution and relational migrations.
- `pytest`: Golden test suite with 40+ spoken gym phrases covering slang, plate math, compound sets, and bodyweight edge cases.

---

## 3. Constitution Compliance Check

- **Principle I (Self-Hosted Architecture)**: 100% compliant. Parsing and alias matching execute in local Python processes on user hardware.
- **Principle II (Source Isolation)**: 100% compliant. Gym logging is isolated in `src/services/gym_parser.py` and `src/api/gym.py`, outputting standardized domain records to `strength_sets`.
- **Principle III (Multimodal Ergonomics)**: 100% compliant. Minimal-friction voice-to-text with clear intermediate preview, plate math normalization, and explicit confirmation.
- **Principle IV (Unified Volume Modeling)**: 100% compliant. Captures `reps_completed`, `weight`, `is_bodyweight`, and `added_weight` so that total volume load and peak PR detection can compute exact work.
- **Principle V (AI Coaching & Feedback)**: 100% compliant. Stores raw transcripts and RPE metrics for retrospective training analysis.
